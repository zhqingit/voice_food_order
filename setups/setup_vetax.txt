On voxeats-server, don't ship the credentials file at all. Use the service account attached to the VM:

  1. Confirm the SA is attached:
  gcloud compute instances describe voxeats-server --zone=us-central1-a \
    --format="value(serviceAccounts.email,serviceAccounts.scopes)"
  1. You should see restoai-vertex@... (or whatever you named it) and cloud-platform in scopes. If not, attach it per the migration doc Phase 0 step 5.
  2. Remove the credentials mount and env var from the production docker-compose.yml:
  # delete these two lines:
  #   GOOGLE_APPLICATION_CREDENTIALS: /gcp/adc.json
  #   - /home/qzhang/.../application_default_credentials.json:/gcp/adc.json:ro
  2. With nothing set, google.auth.default() automatically falls through to the GCE metadata server, which mints a fresh token from the attached SA on every request. No file, no expiry, no re-login ever.
  3. docker compose up -d and you're done.

  The GOOGLE_CLOUD_PROJECT and GOOGLE_CLOUD_LOCATION env vars stay — those are needed regardless of how you authenticate.


  Every GCE VM has a built-in metadata server at 169.254.169.254. When your VM has a service account attached and the Google client libraries can't find an explicit credential, they automatically query the metadata server and get back a short-lived token signed by that
  service account. The metadata server keeps minting new tokens forever — no expiry from a user perspective, no file to refresh, no reauth.

  User-account ADC (what you have now) doesn't have this property. Service accounts via metadata server do.

  Step 1. Confirm the SA is attached to voxeats-server

  - email: restoai-vertex@voxeats.iam.gserviceaccount.com
    scopes:
    - https://www.googleapis.com/auth/cloud-platform

  Keeping local dev working without breaking production

  The challenge: you want the credentials mount on your laptop (no metadata server there) but not on the VM. Solutions, cleanest first:

  Option A (recommended): split into base + override

  docker-compose.yml (committed, production-safe) — drop the credential lines:
  services:
    api:
      environment:
        # GOOGLE_APPLICATION_CREDENTIALS removed
        GOOGLE_CLOUD_PROJECT: voxeats
        GOOGLE_CLOUD_LOCATION: us-central1
        # ... rest unchanged
      volumes:
        - ./app:/app/app
        # credential mount removed
        # ... rest unchanged

  docker-compose.override.yml (in .gitignore, only on your laptop) — adds back the dev-only ADC:
  services:
    api:
      environment:
        GOOGLE_APPLICATION_CREDENTIALS: /gcp/adc.json
      volumes:
        - /home/qzhang/.config/gcloud/application_default_credentials.json:/gcp/adc.json:ro

  Docker Compose loads docker-compose.override.yml automatically when you run docker compose up from the same directory. On the VM, that file doesn't exist, so the override is silently skipped.

  Bonus: I made the volume path point at the gcloud-managed file directly, so future gcloud auth application-default login runs are picked up immediately without copying.

  Option B: profiles

  Tag the credential mount with a profile (profiles: ["devauth"]) and only run docker compose --profile devauth up locally. More verbose, less idiomatic.

  Recap

  - Why your error happens: user ADC tokens have a session lifetime, file-based ADC stops working when that runs out.
  - Why metadata-server SA tokens are permanent: GCE issues them on demand, forever.
  - Production fix: SA attached + roles/aiplatform.user + remove the credential file from the prod compose.
  - Local dev stays unchanged if you split into base + override, with the override gitignored.
